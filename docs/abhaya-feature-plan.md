# Abhaya Libre feature refactor: every OpenType feature through lankafea

> Status (2026-11-19): **Sinhala done and merged.** Abhaya's Sinhala features are generated
> by lankafea (Phases 0–4, Phase 5 `font-config.md`); the hand-written Sinhala features and
> prefix are gone. Merged to Abhaya `dev` and sinhala-font-tools `gh-pages`. Standard 2.0.0
> names the ෆ alternates `fpa` (D6); the Lith ten-ligatures are off by default (D9).
> Real-build comparison: 0 unexplained differences; fontspector 0 FAIL, warnings unchanged.
> 2026-11-26: A3 reverted (kept as before, lankafea `prenasalisedZwj`) and `da_yansa_oosign`
> renamed `dyaa_virama._c`, formed under ss01/dlig (Y1).
> **Open for review:** §4 (A1, A2, P2, T2) and §5 (Q2–Q4). Still to do: Tamil track,
> Phase 3's name check against the standard, `abhaya-case-study.md`.

The goal is to replace Abhaya Libre's hand-written OpenType features with
features **generated by lankafea**, so Abhaya stops being a one-off and becomes
an ordinary consumer of the LankaGlyphset standard. Where Abhaya does something
the generator can't express yet, the fix goes into lankafea (a generator, or a
per-font data file it reads), not back into hand-written code.

Sinhala and Tamil are **separate tracks**. Tamil is Abhaya's step in the Tamil
parity plan ([tamil-plan.md](tamil-plan.md), Phase 4); this plan tracks it but
doesn't repeat it.

| Repo | Branch | What changes there |
|---|---|---|
| `font-repos/abhaya-libre-font` | `feature-refactor` (from `dev`) | glyph renames, per-font lankafea data, generated features replace the hand-written ones |
| `sinhala-font-tools` | `feature-refactor` (from `gh-pages`), in a separate worktree at `../sinhala-font-tools-feature-refactor` | new generators and per-font data support in lankafea; documentation |
| `lanka-glyphsets` | `main` | this plan; standard changes only if a gap turns out to be in the standard |

The sinhala-font-tools worktree is separate so the main checkout, where other
work on the Tamil migration is going on, isn't disturbed. lankafea's sibling
lookups (`../lanka-glyphsets/glyphsets`, `../font-repos`) resolve the same way
from it.

## 1. What exists today

### 1.1 Abhaya's features

Source: `sources/AbhayaLibre.glyphspackage/fontinfo.plist`, 1238 glyphs.

- **Prefixes:** `Languagesystems` (DFLT, latn, sinh, taml, tml2); a Sinhala
  prefix of 830 lines with 31 lookups and 9 classes; a Tamil prefix of 137
  lines with 6 lookups.
- **Features (28 blocks):**
  - Latin: `ccmp` (dotless i/j), `aalt`, `sups`, `numr`, `frac`, `ordn`, `onum`,
    `liga` (all of these except `ccmp` are Glyphs-automatic), and `lnum`
    (hand-written).
  - Sinhala: `akhn`, `vatu`, `rphf`, `pstf`, `rlig`, `abvs`, `blws`, `psts`,
    `dlig`, `dist`, `ss01`, `ss02`, `ss03`, `ss07`, `ss08`. `akhn` is also
    defined a second time, inside the prefix (`sin_touch`).
  - Tamil: `akhn`, `abvs`, `psts` (all with `script taml;` and `script tml2;`),
    and `ss09` (traditional orthography).

### 1.4 Hand-written problems found during the survey

These are bugs or leftovers in the current features, independent of the
refactor:

- **B1** `sinblws_1`: `cCa ු → cU` drops a ca; `cCU-sinh` exists.
- **B2** `sin_lithnum_zero` (`rlig`, on by default): `sinNinelith sinZerolith →
  sinEight_Zerolith`, so ෯෦ shows as eighty. `ss07` has it right.
- **B3** `aalt` lists `abvs` and `psts`, which pulls the Sinhala and Tamil
  vowel ligatures into Access All Alternates.
- **B4** `sin_da_subscripts` has duplicate rules and runs in both `dlig` and
  `ss01`.
- **B5** ~~Archaic number glyphs (`archaicone-sinh` …) have no Unicode value~~.
  **Fixed 2026-11-17:** encoded at U+111E1–U+111F4, as in the standard.
- **B6** ~~Lith digits are named `sinZerolith` …~~ **Fixed 2026-11-17:** renamed
  to `lithzero-sinh` … with `python -m lankafea.migrate` (now able to rename Sinhala
  glyphs; alias table in `tests/fixtures/sinhala-aliases/abhaya.yaml`). The ten-ligatures
  `sinOne_Zerolith` … became `lithone_lithzero-sinh` …, following the naming rule for
  ligatures of encoded glyphs (the standard doesn't list them yet). 19 glyphs, 147
  references; `make build` passes, and ෧෦, ss07 and ss08 shape as before.

Found by the Phase 0 harness (checked against the real build):

- **B7** ~~ක + ෞ shows ෟ before the consonant and no kombuva~~. **Fixed
  2026-11-17 by B8:** HarfBuzz only decomposes ෞ into ෙ + ෟ when the font
  encodes ෟ. Without it ෞ stayed whole and `si_split_matra` turned it into the
  ෟ tail in the pre-base position. The rebuilt font gives `ෙ ක ෟ`, and so do the
  generated features, so nothing needs generating (G7 closed).
- **B8** ~~ෟ (U+0DDF), ෲ (U+0DF2) and ෳ (U+0DF3) aren't encoded~~. **Fixed
  2026-11-17:** `vocaliclsign-sinh`, `vocalicrrsign-sinh` and `vocalicllsign-sinh`
  are encoded, as in the standard (Q7).
- **B9** On a touching cluster with a repaya (ර්‍ක‍්ක), the repaya stays plain
  after the **first** consonant. The `touch_reph*` lookups, which were meant to
  move it to the middle, never match under HarfBuzz, so they are dead code.
  **Resolved 2026-11-17 (Q5):** what they meant to do is now Abhaya's inject
  data, `sources/lankafea/touch-reph.yaml` (T1 in §4). The hand-written lookups go
  in Phase 4 with the rest.
- The hand-written features also keep the ZWJ of a touching cluster in the
  glyph stream (`sub zerowidthjoiner virama-sinh' by touch-sinh`). HarfBuzz hides
  it, so nothing visible comes of it.

## 2. Decisions

- **D1 Plan home** (2026-11-17): this file, next to `tamil-plan.md`.
- **D2 Positional reph and candrabindu variants** (2026-11-17): **data-driven**.
  Abhaya keeps a YAML of classes and context → variant mappings, and lankafea
  generates the lookups from it, with no design change. Moving to GPOS anchors
  is filed for later as
  [abhaya-libre-font#106](https://github.com/mooniak/abhaya-libre-font/issues/106).
- **D3 When generated and hand-written behaviour disagree** (2026-11-17): **the
  standard wins.** Bugs are fixed rather than reproduced. Every visible change
  is listed in §4 for review before the hand-written features are removed.
  Font-specific values (such as the `dist` amount) go in per-font data.
- **D4 sinhala-font-tools branching** (2026-11-17): a separate worktree (see
  the table above).
- **D6 The ෆ alternate is `fpa`** (2026-11-17, Q6): ෆ written as ප + f is named
  `fpa`, in the standard and in Abhaya. The standard's ss02 Fa became `fpa`, `fpI`,
  `fpIi` (was `fPa`, `fPI`, `fPIi`). Abhaya's `.hist` family was renamed to match:
  `fa-sinh.hist → fpa-sinh`, and so on for `fp` (+ virama), `fpI`, `fpIi`, `fpU`, `fpUu`,
  `fpR`, `fpRa`, `fpRI`, `fpRIi` and `fpa_repha`. The standard lists only the first
  three; the rest are Abhaya's own extras for now.
- **D7 Encode ෟ ෲ ෳ** (2026-11-17, Q7). Done (B8), and it fixed ෞ (B7).
- **D8 Repaya on a touching cluster** (2026-11-17, Q5): do what the dead
  `touch_reph*` lookups meant to do (T1). The kombuva on a touching cluster (T2) is
  still open.
- **D9 Lith ten-ligatures off by default** (2026-11-19, Q1): `෧෦` stays two digits in
  default text; the ten-ligatures form only under `ss07` (with ASCII digits or Lith digits).
  Abhaya's `sources/lankafea.yaml` has `numerals: {lith: ss07, archaic: ss08}`, no `lithTens`.
  This also retires B2/A5 in default text (ss07 gives ninety).
- **D5 Latin features (proposed, not confirmed):** out of lankafea's scope.
  Keep them Glyphs-automatic, and make `lnum` automatic too if Glyphs
  generates the same thing. `ccmp` dotless i/j stays hand-written, or becomes
  automatic if Glyphs' `ccmp` covers it. lankafea's preservation model
  (ownership markers) keeps them intact on writeback.

## 3. Phases

### Phase 0: Sinhala parity harness (sinhala-font-tools) — done 2026-11-17

There is a Tamil acceptance test (`tests/acceptance_tamil.py`) but no Sinhala
one, and nothing in Abhaya's Sinhala features should change without one.

- `tests/acceptance_sinhala.py`, modelled on the Tamil one: shape a test
  corpus with the committed Abhaya build and with a font compiled from the
  generated features (same glyph names and cmap), and diff the glyph strings.
- Corpus: consonant × sign grid (ි ී ු ූ ා ැ ෑ ෘ ෲ ් and the split vowels),
  every conjunct and touching pair in the standard, reph on every carrier
  (plain, conjunct, ි/ී, touching), yansaya and rakar with every sign, da-shape
  forms, numerals, and `sinhala-font-tools/test-texts/`.
- Run under default features and under each `ssNN` and `dlig`.
- Output: a categorised difference report. Every difference has to be either
  fixed or listed in §4.
- Use the report to decide G2 (is `C repha ් zwj C2` ever produced by
  HarfBuzz's reordering?) and A4 (does HarfBuzz decompose the split vowels
  before `pstf`, which would make `si_split_matra` dead?).

**Result.** `tests/acceptance_sinhala.py` and `test_sinhala_acceptance.py`
compile the hand-written features and the generated ones into one synthetic font
(the source's glyph names and cmap) and shape 15,543 strings, about 3 seconds per
run. The baseline is frozen in `tests/fixtures/sinhala-baselines/abhaya.fea`
(re-freeze after any rename in the source). **Every difference falls into a known
category, so there are 0 unexplained.** The test fails on any new one.

Numbers as of 2026-11-18, after B7–B9, D6 and G6 (A4 is gone: ෞ now shapes the same
in both; T1 now compares the old plain repaya with the touch-reph data; G6 is gone:
the Da forms are no longer on by default, so the strings it covered now fall
under other items or match):

|---|---|---|
| default | 13,194 / 15,543 | T1 925, C1 663, T2 275, A3 248, A2 119, G3 56, reach 31, P1 21, S3 9, A1 2 |
| `dlig` / `ss01` | 191 / 321 each | G5 43, T1 29, C1 23, reach 18, T2 13, A2 3, A3 1 |
| `ss02` | 0 / 267 | S2 267 (not generated yet) |
| `ss03` | 0 / 9 | S1 9 |

What Phase 0 settled:

- **A4 reversed.** HarfBuzz splits ේ ො ෝ into ෙ plus *the original character*
  and expects `pstf` to replace that with the tail (Uniscribe did the same).
  The generator already does this correctly. The only split-vowel difference was
  ෞ, where both versions were wrong; encoding ෟ fixed both (B7).
- **G2 isn't needed.** Every conjunct in the standard under a repaya shapes the
  same without those 12 rules (the only differences there are A3), so they can go.
- **G6 is new.** lankafea puts the da-shape `._c` forms in default `blws`, but
  the standard lists them under **ss01 Da Forms**, and Abhaya agrees. This is a
  lankafea bug, so they move to `ss01` (Phase 1). Done 2026-11-18.
- **T1 and T2 are new design questions** about touching clusters (see §4 and §5).
- C1 is only the `dist` amount (−113 vs −90). "reach" (23) is rakar ligatures such
  as `ndRa` that the font has but its own features never form.

### Phase 1: Generator gaps (sinhala-font-tools)

Productive rules that belong in the generator for every font, presence-gated:

- ~~**G1** third-order yansaya + repha chains~~: not needed. HarfBuzz puts the repaya
  right after the base consonant, so `yasign aasign repha` never occurs; ර්‍ක්‍යා shapes
  as `ka yasign_repha aasign` with both feature sets.
- ~~**G2** reph inside a ZWJ conjunct~~: not needed.
- ~~**G3** `.rasign` sign variants~~: done 2026-11-19 (`RakarSignVariants`, blws). The
  variants are in the standard's Kernel tier.
- ~~**G4** variant bases~~: not needed. `fpa` exists only after ss02 has run, which is
  after every ligature, so `fpa + usign` never occurs; ss02 maps the formed glyph instead
  (`fU → fpU`, S2).
- ~~**G5** yansaya Da forms~~: done 2026-11-19 (in `DaShape`). `da_yansa_oosign`'s old rule
  (`da esign yasign aasign`) never matched, because the kombuva is reordered before the
  consonant. 2026-11-26: the glyph is da + yansaya + ා + ් (the ෝ without its kombuva), so it
  was renamed to the standard's `dyaa_virama._c`, which `DaShape` already forms (Y1).
- ~~**G6** da-shape `._c` forms go to `ss01`~~: done 2026-11-18. One `DaShape`
  lookup in the stylistic set the standard names ("ss01 Da Forms"), out of default
  `blws`/`psts`. Abhaya's `dlig` copy is `assign` (`DaShape → dlig`, mode `copy`),

  a stylistic set runs after `psts`, the ෝ tail is matched as `aasign_virama` as
  well, so දෝ gets `daa_virama._c` under ss01/dlig, which Abhaya draws but its
  hand-written features never formed (counted as "reach"). The harness no longer
  treats G6 as known, so a `._c` form in default shaping fails the test.
- ~~**G7** ෞ~~: closed. With ෟ encoded, HarfBuzz decomposes ෞ itself (B7).
- Drop G2 (not needed, see Phase 0).

### Phase 2: Per-font data (sinhala-font-tools + Abhaya)

**Done 2026-11-19.** One per-font file in the font repo, `sources/lankafea.yaml`, read by
the CLI (the Glyphs plugin doesn't read it yet). Reference: `font-config.md` in
sinhala-font-tools. It extends the existing `assign`
(feature routing) and `inject` (extra rules) mechanisms rather than adding a
third one.

- **C1 Values:** the `dist` amount.
- **C2 Routing:** which generated group goes to which feature (`DaShape → ss01`
  and/or `dlig`), and `ssNN` names (`featureNames`).
- **S1/S2 Alternate sets:** "every ෆ form `fX` is replaced by `fpX` in `ss02`"
  (D6), plus named ligature sets (ං + ශ in `ss03`).
- **S3 Numeral sets:** ASCII digits → Lith digits (`ss07`) and → archaic
  numbers (`ss08`), generated from the standard's numeral data; Lith
  ten-ligatures gated on presence. Whether Lith
  ligatures belong in `rlig` (always on) or only in `ss07` is a question for
  review (§5).
- **P1 Positional variants:** classes plus rules of the form "in context X, the
  mark becomes variant N". Step one is to express Abhaya's 31 rules as
  presence-gated inject YAML, which the existing inject schema (contextual
  `'` inputs, classes) can already do. **Touching clusters done 2026-11-17:**
  `sources/lankafea/touch-reph.yaml` in Abhaya (T1), passed with `--inject
  sources/lankafea`. It needed one lankafea fix: a contextual rule with one marked
  input and several outputs (`sub touch ka_repha' by ka repha-sinh.001`) is now a
  multiple substitution, not a broken ligature. **Done 2026-11-19:**
  `candrabindu.yaml` (as before) and `vowel-reph.yaml`. The old `matraI_matraII_reph` was
  dead code too: the repaya ligates onto the consonant before ි/ී does, so ර්‍කි showed
  `ka_repha` with a separate ි, the repaya colliding with the loop. The data does what it
  meant: `kI + repha-sinh.006` (`.007` ථ ඨ ඪ ඵ, `.008` ණ). Listed as P2 in §4. Step two: where the classes can be
  derived (touching pairs and ි/ී carriers from the standard; heights from the
  font's metrics or anchors), lankafea derives them so the YAML only names
  the variants.
